# 0.6.4 preparation and upgrade

Prepared 2026-09-29. The released baseline is annotated `0.6.3`, peeling to
`f23460c62fa3508858c0552557b2860af09f2656`. Read-only remote tag inspection found no `0.6.4`.
This patch prepares that version; it creates or pushes no tag. After reviewed main and required
CI pass, a separate PO release operation must recheck availability and publish an annotated
`0.6.4` at the exact approved candidate. If occupied, report the collision and choose a new
version through that operation. Do not replace a published tag or rewrite history.

The Git tag is the kit version. `_min_copier_version` stays `9.0.0`; tooling and application
versions stay `0.1.0`. This patch adds no dependency, module or deployment transport.

## Native transport

`DEPLOY_HOST` remains the raw allocated host, such as `192.0.2.42` or `2001:db8::42`.
Native SSH receives `user@2001:db8::42`. Native SCP receives
`user@[2001:db8::42]:/opt/services/PROJECT_NAME/infra/`; its host:path parser requires brackets.
The appleboy/ssh-action input remains the raw `${{ secrets.DEPLOY_HOST }}` expression.
Do not bracket the shared secret: the copy step now refuses bracketed input before transport.
Missing `DEPLOY_HOST`, `DEPLOY_USER` or `PROJECT_NAME` fails with the required key named.

The workflow still prepares the target directory and transfers both `infra/compose.base.yml`
and `infra/compose.prod.yml`, using the same SSH options and three attempts with 15/30 second
retry waits. The generated runner is now `ubuntu-24.04`. Job names, action versions, key setup,
dotenv decode, registry login/pull retries, health checks and crash-loop detection are retained.
Other runners and production database backups belong to separate work.

## Existing product update

An orchestrator pin changes new scaffolds only. It cannot repair a workflow already committed
in a generated repository. Copier's `_skip_if_exists` protects owned environment, application,
controller and shared-spec files; it does not exclude `.github/workflows/deploy.yml`.
Use a reviewed update and read back the resulting workflow before admitting IPv6 deployment.
Neither a successful Copier exit nor the new answers revision proves every hunk was applied.

Start from a clean committed product on a review branch or isolated worktree. Preserve product
code in Git and back up the ignored real `.env` through the product's ordinary restricted backup
procedure. Never add real environment credentials to Git. Retain the selected modules.
After the tag is actually published, run from the product root:

```bash
git status --porcelain
git branch before-kit-0.6.4
uvx copier update --defaults --trust --vcs-ref=0.6.4 --conflict=rej
git status --short
git diff -- .copier-answers.yml pyproject.toml uv.lock .github/workflows/deploy.yml
git diff --exit-code before-kit-0.6.4 -- .env.example shared/spec services/backend/src/app services/backend/src/controllers services/tg_bot/src/app
```

The status before updating must be empty. `--defaults` preserves noninteractive execution;
`--trust` permits the template's existing `uv lock` task. Confirm `.copier-answers.yml` still
names the original modules and the intended source, and its `_commit` resolves to the published
tag. Review the new exact tooling commit in `pyproject.toml` and `uv.lock`. Compare ignored
environment bytes against the protected backup locally without printing secret values.

Review the whole workflow diff. Read back the raw host for SSH/action, IPv6 brackets only in
`SCP_HOST`, both compose sources, `/opt/services/PROJECT_NAME/infra/`, the retry bound and
`ubuntu-24.04`. Run the generated product's normal `make setup`, `make lint`, `make typecheck`
and `make tests`; backend integration remains part of its ordinary validation. Commit only
reviewed product changes. No live product update or deployment is performed by this kit card.

### Customized workflows

Copier performs a real three-way update. In the tested cases a local workflow name survives
while the transport and runner update. With `--conflict=rej`, an overlapping local runner change
to `self-hosted` is recorded as a rejected local hunk in `.github/workflows/deploy.yml.rej`;
the working workflow uses the candidate's `ubuntu-24.04`. The original customization remains
in the committed pre-update workflow and the rejection artifact. Copier can exit successfully
with such a rejection.
Inspect every `.rej` and the resulting workflow; do not dispatch deployment with unresolved
hunks or rely on the answers revision alone.

Reconcile each rejected hunk deliberately on the review branch, consulting the committed
pre-update workflow and the candidate template. Accept the Ubuntu pin for this standard
workflow, retain reviewed unrelated product customizations, and ensure any rejected transport
hunk has the native per-consumer host change. Review the reconciled diff and remove the
resolved rejection artifact using the editor before committing. `copier recopy` or a forced
overwrite would discard ownership evidence and is not this update procedure.

## Isolated 0.6.3 proof

Focused reproduction from the kit checkout:

```bash
.venv/bin/pytest tests/copier/test_deploy_transport.py -q
```

The tests generate backend, standalone Telegram and combined products through actual Copier.
Controlled commands exercise the rendered compose-copy step, directory preparation, both files,
target, immediate success, SSH/SCP retry, success on the final attempt and terminal failure.
They check missing configuration and bracket refusal before any command. Native `ssh -G`
configuration and a nonconnecting `scp -S` capture assert hostname and username values, including
IPv4-mapped IPv6 representation. No keys, live SSH connection or GitHub mutation are used.
The unchanged ssh-action raw input is asserted; external appleboy execution is not tested.

The release regression renders exact `0.6.3` and demonstrates that its raw IPv6 destination
passes command capture but installed SCP receives host `2001`. The candidate receives exactly
`2001:db8::42`. Upgrade fixtures generate from the exact annotated baseline, commit synthetic
owned environment/spec/application/controller bytes and customized workflows, then run real
`copier update --defaults --trust --vcs-ref=HEAD --conflict=rej` to the candidate snapshot.
They read back unchanged owned bytes, module selection, candidate revision, unaffected deploy
steps, corrected native transport and preserved/rejected customizations. `uv lock` executes;
Git URL redirection keeps unpublished fixture tooling commits local. No fixture workflow is
hand-patched to install the fix.

For manual prepublication review in an isolated fixture, substitute the reviewed immutable
candidate SHA for `0.6.4` in the update command and use a local kit Git source containing both
that candidate and `0.6.3`. The source must remain available for Copier's recorded `_src_path`.
The automated fixture uses the repository's existing committed dirty-tree snapshot mechanism.
