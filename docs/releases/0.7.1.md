# 0.7.1 preparation and upgrade

Prepared 2026-10-03. The released baseline is `0.7.0` (annotated tag on `1de7aa6c`); `0.7.1` is the
next free kit core tag. This patch release fixes the generated product's own backend unit tests; it
changes no runtime behaviour and no contract. No card creates or pushes a tag; a separate PO release
operation publishes the tag below after reviewed main and required CI pass. If the tag is already
occupied, report the collision and choose a new version through that operation. Never move or
replace a published tag.

## Defect

A product generated from `0.7.0` that installs a package with `kit add reminders` fails its own CI
unit-test leg (`make tests`, the "Run tests" step of the generated `ci.yml`):

```
FAILED services/backend/tests/unit/test_job_timers.py::test_lifespan_starts_no_loop_without_declared_timers
FAILED services/backend/tests/unit/test_job_timers.py::test_lifespan_starts_one_loop_for_declared_timers_and_stops_it
redis.exceptions.ConnectionError: Error -2 connecting to redis:6379. Name or service not known.
```

The two lifespan tests in `services/backend/tests/unit/test_job_timers.py` (added in `0.7.0` by
codegen-product-kit-22) entered the full application lifespan, which runs `startup_packages` and so
starts every active package's real runtime. Reminders' startup creates its Redis consumer group and
fails fast when Redis is unreachable, which is correct runtime behaviour. The product CI's unit leg
runs with `.env` copied from `.env.example` and no Redis, so the tests failed. With no package
installed nothing connects, which is why the kit's own CI did not see it.

## Fix

The two lifespan tests now replace `startup_packages`, `shutdown_packages` and `start_timer_loop` in
the lifespan module with recording stand-ins: package startup and shutdown are no-ops, and the
timer-loop wrapper still starts the real loop. They start no package runtime and keep their
assertions, now stated against the record:

- package startup runs before the timer loop starts, and the loop is stopped before package
  shutdown;
- exactly one loop when timers are declared, and none (`start_timer_loop` returns `None`) otherwise.

No other template unit test enters the application lifespan: the `client` fixture uses httpx's
`ASGITransport`, which does not run lifespan events, the middleware tests build their own bare
`FastAPI()`, and the tg_bot tests start no package runtime. Reminders, the catalog and the
lifespan itself are unchanged.

## Versions

| Item | Before | After |
|---|---|---|
| Kit core tag | `0.7.0` | `0.7.1` |
| `codegen_kit.CORE_VERSION` (package façade) | `2.1.0` | `2.1.0` (unchanged) |
| Package protocol version | `1` | `1` (unchanged) |
| `codegen-kit-reminders` | `0.4.0`, `requires_core: ">=2.1,<3"` | unchanged; no package release |

`CORE_VERSION` is unchanged because this is a template test fix, not a core contract change, so no
package's `requires_core` is affected and no package release is needed. `_min_copier_version`,
tooling and application package versions stay as they are.

## Orchestrator and existing products

- The orchestrator must move its kit pin (`scheduler.service_template_ref`) from `0.7.0` to `0.7.1`
  after the tag exists, so that products it generates and then extend with a package keep a green
  unit leg. The pin move is a separate orchestrator card.
- New products generated from `0.7.1` need nothing.
- A product generated from `0.7.0` that installs a package needs the test fix. Run a reviewed
  `uvx copier update --defaults --trust --vcs-ref=0.7.1 --conflict=rej` on a clean review branch, as
  described in the [0.6.4 notes](0.6.4.md). `services/backend/tests/**` is template-owned, so the
  update brings the new `test_job_timers.py`; a product that edited that file resolves the `.rej`
  by hand. The fixed tests replace `startup_packages`, `shutdown_packages` and `start_timer_loop` by
  name in `services/backend/src/app/lifespan.py`, which Copier preserves as user-owned: the lifespan
  must import those names as the template's does, which a `0.7.0` lifespan already does. A `0.7.0`
  product without a package is not affected but takes the same update harmlessly.

## Release-tag rule

The rule from [0.7.0](0.7.0.md#release-tag-rule) still holds: a kit core tag and a package tag must
not share a commit. This release has no package tag. The PO operation publishes:

| Tag | Commit |
|---|---|
| `0.7.1` (annotated, kit core) | the merge commit on `main` of the codegen-product-kit-25 pull request |

No package tag is placed on that commit. Before tagging, confirm that the reminders source is
unchanged since its release: `git diff --quiet packages/reminders/v0.4.0 <merge> --
packages/codegen-kit-reminders`.

## Validation

- The fixed lifespan tests: `template/services/backend/tests/unit/test_job_timers.py`, run in a
  generated product by
  `tests/copier/test_package_activation.py::test_generated_core_timer_loop_fires_through_the_jobs_core`
  (fast copier tests).
- Fast regression:
  `tests/copier/test_package_activation.py::test_generated_backend_unit_tests_pass_with_reminders_and_no_redis`
  installs the real reminders source into a generated backend, activates it, and runs the product's
  whole `services/backend/tests/unit` with `REDIS_URL=redis://redis.invalid:6379`. Against the
  `0.7.0` `test_job_timers.py` it fails with exactly the two lifespan tests above (2 failed, 67
  passed); with the fix it passes. It runs in the broad check and in the `test-pytest` job's "Run
  copier tests (fast)" step of `.github/workflows/test-template.yml`.
- Slow regression:
  `tests/copier/test_two_product_package.py::test_product_with_installed_reminders_passes_its_unit_leg_without_redis`
  takes product B (`backend,tg_bot`) with the real reminders wheel installed by
  `kit add reminders --wheel`, copies `.env.example` to `.env` as the generated CI does, and runs
  the CI's "Run tests" command `make tests` with `REDIS_URL=redis://redis.invalid:6379`. It is a
  `slow` test run by the `test-pytest` job's "Run copier tests (slow)" step of
  `.github/workflows/test-template.yml`.
