## Features and preserved compatibility

Catalog format v1 gains library signatures, package actions, recommendations, default resources
and guarded extensions. The unchanged 0.7.1 loader can still read it. Core 2.2 admits optional
action/default-binding metadata under protocol 1. Reminders 0.3/0.4 selection and activation
remain supported with their original manifests; requesting binding support from those versions
fails explicitly. No component is relabeled or rewritten.

`kit add textparse` installs the independently released, plain tg_bot library. Parsing remains
in textparse 0.1.0: English only, explicit clock/zone, three finite forms, no LLM or guessed times.
`kit bind reminders --default` copies the installed resource into a product-owned binding,
declares the timezone schema, and generates caller-aware create/list/cancel handlers, confirmation
and None-result presets. The generated relay reads `reminders.due` with bounded Redis dedupe;
its crash/timeout limits remain those in the [binding contract](../CONTRACTS.md#product-telegram-bindings).

## Review and update sequence

Start from a clean product checkout and create a review branch. The published tag is used by
products after the PO operation; CI uses the full card candidate SHA in its place:

```bash
git status --porcelain
git switch -c core-0-8-review
uvx copier update --defaults --trust --vcs-ref=0.8.0 --conflict=rej
git diff
make setup
make validate-specs
make generate-from-spec
make typecheck
make tests
.venv/bin/kit add reminders
.venv/bin/kit add textparse
.venv/bin/kit bind reminders --default
make generate-from-spec
make validate-specs
make typecheck
make tests
```

The initial status must be empty. Before setup or accepting the update, inspect the complete diff,
saved `.copier-answers.yml`, root tooling requirement/lock, and every rejection/backup/conflict
marker. Copier exit zero alone is insufficient. Stop for review on any `.rej`, `.orig`, unmerged
path or unresolved marker; resolve customized overlap by hand on the review branch. Do not use
overwrite, fresh copy, answer rewriting or conflict suppression as upgrade evidence. Review the
subsequent component install/binding diff separately from the core update.

The updated root `pyproject.toml` and `uv.lock` pin tooling to the resolved template SHA.
`make setup` syncs root/backend/tg_bot from their locks before generation. Commands must use the
product's root tooling environment, with `direct_url.json` and the `framework` import originating
there, rather than a host or old tooling installation.

Copier protects `.env`, `.env.example`, shared model/event specs, and existing service
`src/app/**` and `src/controllers/**`. Their existing bytes survive the native update.
The façade, bot `src/main.py` hooks, no-binding generated seed, service dependency files and
template tests are core-owned. Regeneration replaces generated contracts; it creates controller
stubs only when absent. The supported unmodified old application/controller code requires no hand
edits. Binding YAML and service manifests belong to the product after installation.

The upgrade CI exposed a template-owned unit-test defect after binding: tg_bot's
`test_post_init_and_shutdown_manage_broker` mocked the publisher broker but entered the real
binding relay startup, connecting to Redis in the unit leg. The test now isolates binding
start/stop as well, retaining broker await assertions and adding hook ordering/application
assertions. Failure cases verify broker cleanup and propagated binding errors. A non-slow
bound-product regression runs the generated handler unit file with unreachable Redis; the existing
relay transport/lifecycle and real Redis proofs retain their assertions. This changes only the
template test boundary, not protected product code or runtime startup behavior. Copier brings
the corrected test to the untouched released product before its post-bind unit leg.

Binding declares a schema only. Before using `/remind`, explicitly set the product-wide
`timezone` to an IANA name through the existing capability-protected `/settings/set` API, with
`contract_version: 1`, `scope: product`, and, for example, `value: America/New_York`.
This is a deployment setup step, never an environment fallback or a runtime default. Retain
explicit required settings/secrets, including `REDIS_URL`, `BACKEND_API_URL` and caller capability.
The protected old `.env.example` is not silently refreshed; review current environment contracts
when configuring deployment. No deployment or real Telegram run is part of this release card.
