# 0.7.0 preparation and upgrade

Prepared 2026-10-02. The released baseline is `0.6.4`; `0.7.0` is the next free kit core tag. This
minor release carries the package catalog (`kit add <name>`, see the changelog) and both halves of
reminders running for real users: the core timer loop (codegen-product-kit-22) and the verified
caller identity (codegen-product-kit-23). No card creates or pushes a tag; a separate PO release
operation publishes both tags below after reviewed main and required CI pass. If a tag is already occupied, report the collision and
choose a new version through that operation. Never move or replace a published tag.

## Versions

| Item | Before | After |
|---|---|---|
| Kit core tag | `0.6.4` | `0.7.0` |
| `codegen_kit.CORE_VERSION` (package façade) | `2.0.0` | `2.1.0` |
| Package protocol version | `1` | `1` (unchanged) |
| `codegen-kit-reminders` | `0.3.0`, `requires_core: ">=2,<3"` | `0.4.0`, `requires_core: ">=2.1,<3"` |
| Catalog versions of `reminders` | `0.3.0` | `0.3.0`, `0.4.0` |

`CORE_VERSION` takes one minor bump for two backward-compatible additions: the optional manifest
field `timers` and the façade dependency `codegen_kit.caller_identity`. A package that uses neither
behaves exactly as on `2.0.0`. Reminders `0.4.0` declares `timers: [{job: tick, every_seconds: 60}]`
and depends on `caller_identity`, and therefore admits only core `>=2.1,<3`. The catalog keeps
`0.3.0`, so `kit add reminders` on a core `2.0.0` product still resolves `0.3.0`, while a core
`2.1.0` product resolves `0.4.0`. `_min_copier_version` stays `9.0.0`; tooling and application
package versions stay `0.1.0`.

## What changes in a generated product

- The backend runs one core timer loop when an installed package declares a timer. It fires each
  timer job once per slot with `{"at": <slot instant>}` through the existing `JobsController.fire`
  record-then-emit path, under the identity `core-timer:<job>:<slot instant>`,
  `fired_by_product=APP_NAME` and `fired_by_run=core-timer`. A restart or a second backend process
  firing the same slot dedups on `(fired_by_product, command_id)`. A failed fire is logged
  (`core_timer_fire_failed`) and the loop goes on to the next slot. A missed slot is covered by the
  next slot's later `at`, not replayed.
- With reminders `0.4.0` installed, due reminders reach `emitted` and publish `reminders.due` with
  no `POST /jobs/fire`. Central QA's explicit `POST /jobs/fire` of `reminders.tick` with
  `X-Jobs-Capability` and its own `at` works and dedups exactly as before.
- A product without package timers (no package, or packages without `timers`) generates
  `JOB_TIMERS = {}` and starts no loop, container or worker.
- `job_commands` grows by one row per timer per slot and is not pruned: `86400 / every_seconds`
  rows per timer per day, 1,440 a day (about 525,600 a year) for reminders `0.4.0`.
- The backend core verifies the caller of a package route. A package route depends on
  `codegen_kit.caller_identity`, which requires exactly one `X-Identity-Capability` equal to the new
  backend `generated_secret` `USER_IDENTITY_CAPABILITY`, plus exactly one `X-User-Channel` and one
  `X-User-External-Id`, and answers 401 when any of them is missing or malformed. It resolves the
  identity in `user_channels`, answers 403 for an unknown identity or an inactive user, and gives
  the route the canonical `user_ref` `"<channel>:<external_id>"`, for example `telegram:123456`.
  This is service-level trust inside the product with the tg_bot as the trusted caller, not end-user
  authentication. The product's own routes are unchanged.
- `USER_IDENTITY_CAPABILITY` is declared in the backend env contract with consumers `backend` and,
  in a `backend,tg_bot` product, `tg_bot`. The deployment secret resolver generates and persists it
  like every other `generated_secret`; local `.env` files carry
  `local-identity-capability-not-for-production`. The backend refuses to start without it.
- The generated tg_bot gains `BackendClient.request_as_telegram_user(method, path, telegram_id,
  ...)`, which adds the three headers with the capability from its environment.

The full contracts are [Core timer loop](../CONTRACTS.md#core-timer-loop) and
[Core caller identity v1](../CONTRACTS.md#core-caller-identity-v1).

## Breaking change for reminders callers

Reminders `0.4.0` takes the owner from the verified caller only. `POST /reminders` takes
`{text, remind_at}` and refuses any other field with 422; `GET /reminders` lists the caller's
reminders; `DELETE /reminders/{id}` cancels only the caller's reminder, and another user's reminder
answers 404, the same as a missing one. There is no `user_ref` in a body, query or path, and a
request without identity headers is refused with 401 (403 for an unknown or inactive user). The
stored `user_ref` and the `reminders.due` payload keep the field and carry the canonical form, so a
bot can deliver the due message to that chat. The `reminders.reminder_owner_ref` seed stays an
opaque value; it should be the canonical form, for example `telegram:<id>`, for that user to see
the seeded reminder through the API.

Every existing caller must change: central QA and any existing bot must send the identity headers
instead of `user_ref`. Concretely, the orchestrator's central QA (out of scope here; it comes with
the pin-move card) must, for each reminders request to a product:

1. Ensure an active identity exists: `POST /users/grant` with exactly one `X-Grant-Capability`
   header equal to the product's `USERS_GRANT_CAPABILITY` and the body
   `{"channel": "<channel>", "external_id": "<id>"}`, for example `telegram` and a QA id.
2. Send on every `POST`, `GET` and `DELETE /reminders...` request exactly these three headers:
   `X-Identity-Capability: <the product's USER_IDENTITY_CAPABILITY>`,
   `X-User-Channel: <channel>` and `X-User-External-Id: <id>`, and no `user_ref` anywhere.
3. Expect `user_ref` in responses and in `reminders.due` to be `"<channel>:<id>"`. To check the
   seeded reminder, write `reminders.reminder_owner_ref` as that same canonical value.

`POST /jobs/fire` of `reminders.tick` is unchanged. No stored `user_ref` values are migrated: no
product has reminders `0.4.0` yet.

## Existing product update

New products generated from `0.7.0` need nothing. For an existing product, run a reviewed
`uvx copier update --defaults --trust --vcs-ref=0.7.0 --conflict=rej` on a clean review branch, as
described in the [0.6.4 notes](0.6.4.md), then:

1. Copier's `_skip_if_exists` preserves user-owned `services/*/src/app/**` and
   `services/*/src/controllers/**`. The new `services/backend/src/app/timers.py` is added because it
   does not exist yet, but `services/backend/src/app/lifespan.py` is kept as it was. Reconcile it
   with the template's lifespan: import `JOB_TIMERS` and `start_timer_loop`, start the loop after
   `startup_packages(application)`, and stop it before `shutdown_packages(...)`. Without that
   reconciliation the product runs no timer, exactly as on `0.6.4`. The change to
   `controllers/jobs.py` is its docstring only.
2. `codegen_kit/packages.py` is core-owned and updates to `CORE_VERSION = "2.1.0"` and admits the
   `timers` field; `codegen_kit/__init__.py` exports `caller_identity`.
3. The new `services/backend/src/app/caller_identity.py` is added because it does not exist yet.
   `services/backend/src/core/settings.py` requires `USER_IDENTITY_CAPABILITY`, and `.env` and
   `.env.example` are preserved, so add
   `USER_IDENTITY_CAPABILITY=local-identity-capability-not-for-production` to both by hand; without
   it the backend does not start. Deployments receive the generated secret from the resolver. A
   `backend,tg_bot` product's `services/tg_bot/src/main.py` gains
   `BackendClient.request_as_telegram_user`; reconcile it if the bot was edited, and call package
   routes through it.
4. Run `make generate-from-spec`; `services/backend/src/generated/jobs_schemas.py` gains
   `JOB_TIMERS`.
5. To adopt the timer and the caller identity for reminders, run `kit add reminders` (or `kit add reminders --wheel` with a
   built `0.4.0` wheel), which installs `0.4.0` and regenerates the contract. No migration is added.

## Release-tag rule

The kit core tag and the package tag must be on different commits. Copier records the template
revision as `_commit` with `git describe --tags`, and the orchestrator's template smoke compares
that `_commit` with its pinned kit core tag; with both tags on one commit, `git describe` can
report the package tag and the smoke fails.

For this release the PO operation publishes, in one operation:

| Tag | Commit |
|---|---|
| `0.7.0` (annotated, kit core) | the merge commit on `main` of the codegen-product-kit-23 pull request (caller identity) |
| `packages/reminders/v0.4.0` (annotated, package) | the head commit of the codegen-product-kit-23 pull request |

These are two different commits. The codegen-product-kit-22 merge (`8c45937c`) is not tagged: its
reminders `0.4.0` still accepts `user_ref` and is not the released package. Before tagging, confirm
that the package source is byte-identical on both commits: `git diff --quiet <head> <merge> -- packages/codegen-kit-reminders`. Publish both tags together:
after this merge the live catalog lists `0.4.0`, and until `packages/reminders/v0.4.0` exists
`kit add reminders` on a core `2.1.0` product refuses it as not published yet. Moving the
orchestrator's kit pin (`scheduler.service_template_ref`) to `0.7.0` is a separate operation.
