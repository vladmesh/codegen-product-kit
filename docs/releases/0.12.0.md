# 0.12.0 preparation and upgrade

Prepared 2026-10-25. The released baseline is annotated `0.11.0` (object
`705f3ce5bd182a6f6700c73997b34c51089d53a5`, peeling to
`59a0752c8f44c01c04054f9bbe0bd699d3d27dd9`); read-only remote inspection found no `0.12.0`.
This kit minor covers everything merged to main after `0.11.0`. It is prepared, not published:
this work creates no tag, updates no product and deploys nothing. Publication is the later PO
operation below.

## Versions

| Item | 0.11.0 | 0.12.0 |
|---|---|---|
| Kit core tag | `0.11.0` | `0.12.0` (prepared, no tag) |
| Generated façade `CORE_VERSION` | `2.6.0` | `2.6.0` |

| Tooling/application distribution | `0.1.0` | `0.1.0` |
| Minimum Copier | `9.0.0` | `9.0.0` |

The kit tag, the façade semver, the package protocol and the distribution version are
independent identifiers; this release changes only the first. The minor bump marks the new
explicit installation form below; no template file changed in this range. Package releases are
separate annotated tags on their own commits and are not part of this tag: reminders `0.5.0`,
textparse `0.1.0` and tg-channels `0.1.2` and their catalog entries are unchanged,
`packages/pending-releases.yaml` is empty, and this release publishes no package.

## Contents

- `kit add <name> --package-source <dir> --product-root <root>` (Python API
  `framework.cli.add_source_package`) installs a protocol-v1 runtime package that is in no
  catalog from source the product owns, for example `packages/<name>/` with its own tests. The
  directory, after resolving symlinks, must lie inside the product root and outside any nested
  product; no catalog, tag or catalog environment variable is read, and mixing it with `--wheel`,
  `--catalog-source` or `--catalog-ref` is a usage error.
- Before any write, the source's static `pyproject.toml` identity (distribution, version, one
  `codegen_kit.packages` entry point named `<name>`), its `package.yaml` and default binding, the
  `requires_core` admission of the product façade and the host contract are checked. After
  `uv build`, the wheel's METADATA distribution and version, entry point, manifest and default
  binding must equal the source's. A refusal leaves the product's installation files unchanged.
- The verified wheel then takes the ordinary path: copy under `services/backend/packages/`,
  backend dependency and lock, deptry exemption, manifest allowlist, frozen backend sync and
  contract generation. Activation, `kit bind` and generated CI treat it like a released package,
  and a fresh checkout restores it from the committed wheel and lock alone. See
  [package installation](../CONTRACTS.md#installation-discovery-and-activation).
- The slow Copier lane (`tests/copier/test_source_package_install.py`, CI only) copies the
  synthetic package and the tg-channels source into a generated backend,tg_bot product, installs
  both through the product's own `kit`, repeats one install, binds the default, restores the
  backend from the committed wheels and lock and checks that regeneration leaves the generated
  contracts unchanged. It proves that local install path in one generated product; it is no
  orchestrator install, deployment or product migration proof.
- Kit CI only: both `test-pytest` Copier steps set `TMPDIR` to `runner.temp`, so the job's
  temporary products, environments and wheels stay off the runner image's `/tmp`, whose per-user
  quota they exceeded ([kit CI](../TESTING.md#ci)). Generated products are
  unaffected.

The [changelog](../../CHANGELOG.md) section `0.12.0` lists each change.

## Existing products

A generated product takes this release after publication through the reviewed Copier update,
which rewrites the root tooling requirement to the tag's commit and relocks it:

```bash
git status --porcelain                # must print nothing
git switch -c kit-0-12-review
uvx copier update --defaults --trust --vcs-ref=0.12.0 --conflict=rej
git status --short
find . -name '*.rej' -not -path './.venv/*'
git diff
make setup
make generate-from-spec
```

From `0.11.0` the update changes only the tooling pin and lock; a product on an older release
also takes every earlier release's changes and follows those notes, starting with
[0.11.0](0.11.0.md#existing-products). Copier keeps the product-owned files and the saved
answers ([upgrading a generated product](../CONTRACTS.md#upgrading-a-generated-product)).
Package sources under `packages/` and their tests are not template files, and installed wheels,
bindings and product settings stay as they are. Copier can exit zero with rejected hunks: review
every changed hunk, reconcile each `.rej` by hand, run the product's `make lint`,
`make typecheck` and `make tests` in its own CI route and commit the reviewed update. Nothing
migrates a product automatically.

New products can scaffold from the immutable `0.12.0` tag once it is published.

`--package-source` is a local product operation only. It adds no orchestrator INSTALL support
for local sources, no ranking capability, no candidate recording and no reuse across products.
Unreviewed source stays in its product. Promoting it to a shared package still requires the
owner's personal code and security review and the normal independent package release
([pending releases](../CONTRACTS.md#pending-releases)).

## Publication

After this preparation is reviewed and merged and its postmerge Framework CI, Test Copier
Template (with the slow `test-pytest` lane, including the source install case) and Runner Proof
(`fresh` and `coexistence`) runs on that merge succeed, the PO operation runs:

```bash
git fetch origin main --tags
release_commit=<reviewed-merge-sha>
git merge-base --is-ancestor "$release_commit" origin/main
git ls-remote origin refs/tags/0.12.0          # must print nothing
git tag --points-at "$release_commit"          # must print no packages/* tag
git tag -a 0.12.0 "$release_commit" -m "kit core 0.12.0"
git push origin refs/tags/0.12.0
git ls-remote origin refs/tags/0.12.0 'refs/tags/0.12.0^{}'
```

The peeled readback must equal `release_commit`, and the first line names the annotated object.
Use the reviewed merge commit on main, never a PR merge projection or an unmerged candidate.
Never move an existing tag, force-push, or put a package tag on that commit. If `0.12.0` exists
or conflicts, stop and choose a new version through that operation.

Separate work after publication: the orchestrator's kit tag pin, its tooling requirement and
lock, any catalog activation and its generated product fixtures.
