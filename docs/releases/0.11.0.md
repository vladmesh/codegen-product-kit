# 0.11.0 preparation and upgrade

Prepared 2026-10-19. The released baseline is annotated `0.10.1` (object
`902ae4aaddc48665f18297b8994e04b1be9c2d6a`, peeling to
`f7de8f96b18f79b94dcd0546905771674cf11cfa`); read-only remote inspection found no `0.11.0`.
This core minor covers everything merged to main after `0.10.1`. It is prepared, not published:
this work creates no tag, updates no product and deploys nothing, and no speedup of the
generated CI or deploy workflows has been measured. Publication is the later PO operation
below.

## Contents

- Core host contract, façade 2.5.0: core owns the product-scoped `language` setting, one
  generated tg_bot registry registers core, product (`ProductCommand`) and bound module commands
  and answers unknown input in RU/EN, a hard lint refuses conflicts and registration bypasses,
  the application's handlers are sealed at runtime, and `kit check-install` is a read-only
  preflight. See [the core host contract](../CONTRACTS.md#core-host-contract-v1) and
  [the read-only install preflight](../CONTRACTS.md#read-only-install-preflight).
- Façade 2.6.0, additive: `ProductText` and `ProductCallback` with `p:` callback data in
  `services/tg_bot/src/commands.py`; a product without them registers as before. See
  [the command registry](../CONTRACTS.md#command-registry).
- Generated products prepare every Python environment through `scripts/prepare-env.sh`, which
  fails fast on an unknown, missing or failed environment, and `make typecheck` fails when any
  service fails ([development](../DEVELOPMENT.md#changing-the-copier-template)).
- The generated settings and users routers commit before they answer or publish, so a read right
  after a `200` sees the write ([core settings](../CONTRACTS.md#core-settings-v1)).
- The required runner proof with its `fresh` and `coexistence` legs and explicit proof and catalog
  modes, defaulting to published tg-channels 0.1.2
  ([runner proof](../RUNNER_PROOF.md)); pending package releases and tag-bound catalog checks
  ([pending releases](../CONTRACTS.md#pending-releases)).
- Generated PR CI runs `quality`, `dev-smoke` and, with backend, `integration` as sibling jobs
  behind the required `lint-and-test` aggregate, which passes only when every result is `success`
  ([generated projects](../TESTING.md#generated-projects)).
- The generated deploy step uses the runner's native `ssh` and waits with
  `up --wait --wait-timeout 120 --remove-orphans` instead of a fixed sleep
  ([infrastructure](../../template/infra/README.md#deployment-host-and-workflow-updates)).
  `DEPLOY_USER` and `DEPLOY_HOST` form the SSH destination; `PROJECT_NAME`, `DEPLOY_PORT`,
  `DOTENV_B64` and the three registry values reach the remote script as quoted standard-input
  assignments. That quoting covers the deploy step only and does not make arbitrary values safe
  in the earlier compose-copy step, which is unchanged.
- Kit CI pulls Docker Hub images through `mirror.gcr.io`; this is kit CI only.

The [changelog](../../CHANGELOG.md) section `0.11.0` lists each change in full.

## Existing products

Products generated from an earlier façade take this release after publication by native Copier
update, reviewed like any other change:

```bash
git status --porcelain                # must print nothing
git switch -c kit-0-11-review
# back up ignored real .env and infra/.env* through the product's restricted procedure
uvx copier update --defaults --trust --vcs-ref=0.11.0 --conflict=rej
git status --short
find . -name '*.rej' -not -path './.venv/*'
git diff
make setup
make generate-from-spec
```

Keep the selected modules; Copier reuses the saved answers. Copier protects the product-owned
`services/tg_bot/src/commands.py`, `services/*/src/app/**`, `services/*/src/controllers/**`,
`.env`, `.env.example` and the shared specs, and bindings and manifests are not template files
([upgrading a generated product](../CONTRACTS.md#upgrading-a-generated-product)). Read back the
retained owned files and the backed-up environment data without logging secrets. Unrelated
product settings and real application or environment data stay as they are.

Copier can exit zero with rejected hunks. Before claiming success, review every changed hunk of
the kit-owned files, in particular `.github/workflows/ci.yml` (sibling jobs and the
`lint-and-test` aggregate), `.github/workflows/deploy.yml` (native SSH, required values and the
readiness wait), the façade, the generated registry, `scripts/prepare-env.sh`, Dockerfiles, and
the tooling requirement and lock, and reconcile every `.rej` by hand. A local workflow change
overlapping a changed hunk lands in a `.rej`. Then run the product's `make lint`,
`make typecheck` and `make tests`, and `make test-integration` for backend shapes, in its own CI
route, and commit the reviewed update.

Core owns `language` and the command registry. Product commands, the text handler and callbacks
are declared only in `services/tg_bot/src/commands.py`; the lint refuses direct handler
registration. A retained manifest that declares `language`, a binding that claims it, or a
product command that collides with a core or bound command fails generation and lint, naming
the conflicting sources. Repair it in a reviewed explicit edit: remove the manifest declaration, rename the
product command, or rebind; nothing overwrites a product declaration automatically.

The released-core upgrade proof copies genuine annotated `0.7.1` (façade 2.1.0) and updates it
to the candidate in the slow Copier lane; a fast case updates a façade 2.5.0 main commit with a
product command. Neither is an update from a published `0.10.1` product or a production
migration, and customized products need the review above.

## Publication

After this preparation is reviewed and merged and its postmerge Framework CI, Test Copier
Template (with the slow `test-pytest` lane, including generated-product and released-core
upgrade cases) and Runner Proof (`fresh` and `coexistence`) runs on that merge succeed, the PO
operation runs:

```bash
git fetch origin main --tags
release_commit=<reviewed-merge-sha>
git merge-base --is-ancestor "$release_commit" origin/main
git ls-remote origin refs/tags/0.11.0          # must print nothing
git tag --points-at "$release_commit"          # must print no packages/* tag
git tag -a 0.11.0 "$release_commit" -m "kit core 0.11.0"
git push origin refs/tags/0.11.0
git ls-remote origin refs/tags/0.11.0 'refs/tags/0.11.0^{}'
```

The peeled readback must equal `release_commit`. Use the reviewed merge commit on main, never a
PR merge projection or an unmerged candidate. Never move an existing tag, force-push, or put a
package tag on that commit. If `0.11.0` is occupied, stop and choose a new version through that
operation. The orchestrator pin and its renders and locks are separate work.
