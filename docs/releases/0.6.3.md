# 0.6.3 preparation and upgrade

This patch is prepared for a subsequent release operation. The kit version is the Git tag;
`0.6.2` is the released baseline and `0.6.3` is the next tag to create from reviewed merged main.
The old contributor instruction to update the "Copier version" was stale: `_min_copier_version`
remains the Copier tool requirement (`9.0.0`). The tooling distribution and application package
versions remain `0.1.0`; neither is a second kit release source. The existing unreleased CI fix
has been recorded under its already published `0.6.2` tag.

## Backend upgrade

The released core head `d4a7b2c9e1f0` remains in the chain. New revision `e6b8c2d4a901` widens
`users.id`, `user_channels.user_id`, and `settings.subject_id` to PostgreSQL `bigint`, and
`users_id_seq` to bigint with its serial default and ownership retained. Channel/settings surrogate
IDs stay integer. Foreign key cascade, identity uniqueness, setting uniqueness and scope checks,
user status, and string external identities keep their existing semantics. Python/schema integer
contracts already accept these values; no spec regeneration is needed.

For an existing generated product, review its Copier update, then apply its normal `make migrate`
operation against the intended database. The migration alters columns and takes database locks;
schedule that operation with the product's ordinary migration procedure. Do not replace or stamp
over the released revisions. Copier preserves user-owned `services/*/src/app/**`, so reconcile the
`User.id`, `UserChannel.user_id`, and `Setting.subject_id` ORM declarations with this patch's
BigInteger declarations when reviewing the update. SQLite unit fixtures retain the INTEGER
variant for user primary-key autoincrement; PostgreSQL uses BigInteger.

Downgrade to `d4a7b2c9e1f0` locks the three tables and checks all widened columns and the user
sequence before narrowing. It refuses any value outside int32 or a sequence above int32 and
leaves data/types/revision intact through PostgreSQL transactional DDL. It never deletes or
truncates high values or resets a sequence to force a downgrade. Representable data can be
downgraded with its constraints and normal serial inserts preserved.

## Logging

Backend and standalone/combined Telegram startup use `shared.logging.configure_logging`.
`httpx` and `httpcore` log at WARNING even when the application logs at DEBUG. The shared formatter
also redacts Telegram `/bot<token>` and `/file/bot<token>` paths after rendering, protecting foreign
log messages, structured exception messages, and formatted tracebacks in JSON and console output.
Safe method names, service names, error types and statuses remain visible.

## Validation and remaining release work

`tests/integration/test_user_identifiers.py` runs in the generated disposable PostgreSQL stack
through `make test-integration`, collected by the required template CI generation job. It checks
fresh installs, preserving upgrades from the exact released head, independent database readback,
constraints, auto IDs, migration reruns, and successful/refused downgrade paths.
`tests/copier/test_user_safety.py` executes generated logging tests and service typechecks in backend,
standalone Telegram, and combined products through the fast Copier suite. Real httpx/python-telegram-bot calls
use local mock transport responses; no Telegram credentials or network requests are needed.
